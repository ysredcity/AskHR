## 1. 产品目标

### 1.1 产品定位

为企业内部建立 AI 原生人资工作台，以 AskHR 对话作为主要工作入口，采用“左侧导航＋右侧工作区”的统一结构，把政策咨询、个人与组织数据查询、业务办理、任务跟进和辅助分析连接起来。

所有用户使用同一套工作台框架。员工、管理者、HR 和薪酬 COE 的差异用于决定数据权限、可用业务动作及服务大厅入口组合，不再各自形成独立门户或顶层角色视图。

用户既可以从业务页面直接操作，也可以用自然语言表达诉求；智能体应将诉求转为可核实的答案、可确认的业务草稿或可追踪的任务。复杂业务继续由对应专业系统承接。

### 1.2 需要解决的问题

1. 人资服务分散在多个系统，用户需要先知道业务归属和系统名称才能办事。
2. 政策解释与个人数据、实际办理入口脱节，用户得到答案后仍需自行寻找表单。
3. 申请、审批、补材料和结果通知分散，缺少统一进度视图。
4. 管理者难以及时汇总团队出勤、招聘、发展与人才结构信息。
5. HR 和 COE 需要在大量专业菜单与数据之间切换，异常定位和报告准备成本较高。

以上为根据原型结构推导的问题假设，尚未经过用户访谈或真实使用数据验证。

### 1.3 期望结果

- 员工能够以“我要做什么”发起服务，而无需先理解系统组织方式。
- 同一个问题在对话、GUI 页面和业务详情中使用一致的数据与制度口径。
- 高频业务形成“咨询 → 查询 → 草稿 → 确认 → 提交 → 进度 → 结果”的闭环。
- 管理者和 HR 能从汇总指标追溯到授权范围内的明细和处理事项。
- AI 给出的事实有来源，执行的动作有回执，未完成的任务有明确状态。

## 2. 目标用户与使用场景

| 用户 | 核心诉求 | 典型场景 | 建议数据边界 |
|---|---|---|---|
| 员工 | 查政策、查本人信息、办个人业务、学习与发展 | 请假、查工资、开证明、查绩效、找内部岗位 | 本人数据及可公开服务信息 |
| 新员工 | 按阶段完成入职融入与试用期任务 | 找导师、学习、制定试用期目标、自评与转正 | 本人计划及指定支持伙伴 |
| 管理者 | 团队日常管理与人才决策支持 | 审批、出勤异常、HC 缺口、人才盘点、IDP 跟踪 | 授权组织和成员；敏感字段单独授权 |
| HR 业务人员 | 管理业务对象、处理流程与异常 | 组织岗位维护、薪酬社保、招聘录用与人员异动 | 职责范围内组织、业务与字段 |
| 薪酬 COE | 薪酬体系设计、定调薪与分析 | 标准维护、年度调薪、方案审批、薪酬洞察 | 授权薪酬范围与项目 |
| 平台运营人员（建议新增） | 维护知识、服务目录、权限和智能体质量 | 制度更新、路由配置、失败处理、效果分析 | 按运营职责授权，不默认可看员工敏感数据 |

本期只考虑桌面端。用户从统一首页新建对话，或从固定导航进入员工自助、活水平台和服务大厅；已有对话可从侧栏继续。角色切换只在服务大厅内改变可见入口组合，不切换整套工作台，不改变真实权限。

## 3. 范围与证据说明

### 3.1 如何理解原型证据

| 标记 | 含义 |
|---|---|
| 已体现 | HTML 有相应页面、菜单、数据展示或交互逻辑；不代表生产可用 |
| 演示 | 固定回复、内存数据更新、本地存储、通用占位页或提示消息模拟结果 |
| 建议补齐 | 为满足统一智能体目标推导的需求，原型没有形成完整能力 |
| 待确认 | 存在冲突或缺少业务定义，不能据此定为正式规则 |

V0.1 检查了外层五个标签及其 Base64 内嵌页面；本版仅采用桌面端业务证据，结合页面文本、菜单配置、路由和事件函数分析。未进行真实账号登录、后端接口或企业制度核验；未检出这些内嵌页面使用 `fetch` 或 `XMLHttpRequest` 调用业务接口，不能据页面提示判定业务执行成功。

### 3.2 已确认的产品架构约束

1. 暂不考虑移动端。
2. 使用左侧导航、右侧工作区的统一 AI 工作台，不沿用以角色为主的独立视图。
3. 左侧除新对话和对话管理外，固定提供首页、员工自助、活水平台、服务大厅四个 GUI 入口。
4. 首页同时是新对话页，只保留 AI 入口与最基础的任务待办。
5. 员工自助包含个人信息、新员工专区、我的假勤、我的收入、我的绩效、我的发展六个 Tab。
6. 服务大厅通过角色 Tab 展示不同入口组合。角色差异限定在服务组织和权限层，不上升为顶层门户切换。

以上为用户明确要求，优先于原型布局和 V0.1 的页面建议。具体交互默认值与业务实施优先级仍按下文标注评审。

### 3.3 全景范围与建议首期

原型覆盖完整人资门户愿景，不宜将全部菜单视为首期交付承诺。

| 阶段 | 建议范围 | 完成标志 |
|---|---|---|
| P0：首期必须 | 统一工作台框架、四个 GUI 入口与六个自助 Tab、对话管理、身份权限、统一 AskHR、政策问答、本人基础数据与假期查询、服务定位、请假闭环、统一申请与待办跟踪、执行回执和审计 | 选定用户群可以可靠完成至少一个真实办理闭环 |
| P1：后续重点 | 工资查询与敏感信息验证、证明办理、新员工融入、管理者出勤与审批、学习推荐、人工服务交接 | 扩展高频服务，连接员工与管理者协作 |
| P2：扩展能力 | 深度人才分析、内部岗位匹配、薪酬 COE 辅助决策、行业对标、报告资产、复杂跨系统编排 | 在数据和业务规则成熟后逐步开放 |

优先级为本文建议，尚未得到业务确认；在真实接口不可用时，首期相应动作应提供明确的专业系统办理入口，不能以模拟成功代替接通。

## 4. 信息架构与页面结构

### 4.1 统一工作台结构

```text
HiHR AI 人资工作台
├─ 左侧导航（持续可见，可收起）
│  ├─ 新对话（主操作，进入首页空白会话态）
│  ├─ 首页
│  ├─ 员工自助
│  ├─ 活水平台
│  ├─ 服务大厅
│  ├─ 对话管理（搜索、置顶、最近对话）
│  └─ 当前账号与必要设置
└─ 右侧工作区（随当前入口切换）
   ├─ 首页 / 新对话：AI 输入入口＋基础待办
   ├─ 对话详情：消息、引用、业务草稿、执行状态与结果
   ├─ 员工自助：六个 Tab＋对应业务内容
   ├─ 活水平台：职位、筛选、详情、简历、投递记录
   ├─ 服务大厅：角色 Tab＋分类服务入口
   └─ 业务工作页：从服务、对话或待办打开的表单/列表/分析/详情
```

“新对话”是始终可见的快捷动作，“首页”是固定导航项，二者进入同一页面。点击任一入口均进入空白会话态；已有未发送输入或未保存业务草稿时先保存或提示处理，避免静默丢失。未发送内容时不创建空历史记录。发送第一条消息后，右侧转为对话详情并生成可继续的会话记录。

业务表单和分析页由上述入口进入，属于右侧工作区中的二级页面，不增加员工门户、管理者门户、HR 门户、薪酬 COE 门户等顶层入口。

### 4.2 左侧导航与对话管理（WS-01，P0）

- 固定导航按“首页、员工自助、活水平台、服务大厅”排序；当前入口有明确选中态。
- 新对话按钮始终可访问；对话列表有独立滚动区域，长列表不挤出固定导航。
- 对话管理支持搜索、打开、自动命名、重命名、置顶、归档；删除行为和保留期限按企业策略确定。
- 每条对话显示标题与必要状态，例如处理中、待补充、待确认；列表避免显示工资等敏感内容。
- 点击历史对话恢复消息、关联草稿、任务和结果；业务状态读取最新数据，不只恢复旧提示。
- 收起侧栏后仍能访问新对话及四个固定入口，可再次展开查看完整历史。
- 从 GUI 页面切换到会话不丢失已保存状态；未保存表单遵循草稿与离开提醒规则。
- 账号显示在侧栏底部；不设置全局角色门户切换器。

### 4.3 首页＝新对话页（WS-02，P0）

首页只承担两个职责：发起人资业务对话，以及查看最基础的待办。

**AI 入口：**

- 主区域突出人资助手输入框，可输入各类政策问询、个人/团队数据查询和办理诉求。
- 输入框给出简洁提示，如“问政策、查信息，或告诉我你想办理什么”。
- 可在输入框内或附近保留少量示例问题作为 AI 输入辅助，不另设服务卡片区或角色模式选择。
- 用户首次发送后进入当前对话；无需先选择员工、管理者、HR 或 COE 模式。

**基础任务待办：**

- 仅呈现需要当前用户行动的事项，如待审批、待补材料、待完成任务；不把全部申请进度、新闻和运营推荐混入待办。
- 每项显示标题、业务类型、状态/截止时间和“去处理”入口；默认展示最近或最紧急的少量事项，建议最多 5 条，超出可展开全部待办。
- 处理入口打开右侧对应业务详情，必要时可带该事项进入对话。
- 没有待办时显示简短空态；不填充无关推荐模块。
- 全部待办可作为首页下的二级工作页，支持基础筛选，不新增顶层菜单。

**首页不放置：** 收入/团队指标大屏、常用服务墙、新闻头条、学习专区、生日关怀、组织图表和专业管理菜单。保留的业务能力在相应 GUI 页面或对话中访问。

### 4.4 员工自助（WS-03，P0 页面框架；具体业务按原优先级）

固定为六个 Tab，顺序如下；不按用户管理职务更换整套页面。

| Tab | 核心内容 | 与 AI 的衔接 |
|---|---|---|
| 个人信息 | 基础信息、全景档案、信息修改、职业旅程 | 围绕当前字段咨询或发起信息修改草稿 |
| 新员工专区 | 支持伙伴、融入计划、学习任务、试用期目标、转正节点 | 问入职规则、解释任务、协助制定目标 |
| 我的假勤 | 假期余额、考勤日历、异常、请假/补卡/加班及记录 | 查询余额、解释异常、生成办理草稿 |
| 我的收入 | 工资条、收入变化、社保公积金、股权与福利查询 | 解释授权范围内的收入项目和变化 |
| 我的绩效 | 目标/PBC、总结与自评、结果反馈、趋势与申诉 | 解释流程、辅助整理内容、进入申诉办理 |
| 我的发展 | 技能画像、学习、任职资格、认证、IDP、辅导 | 推荐学习或发展动作、查询资格与进度 |

- 初次默认进入“个人信息”；会话内再次访问可恢复上次 Tab，此为建议默认值。
- 个人信息面向全部员工；新员工身份主要决定专区内容和任务。非新员工进入专区时展示适用说明或历史记录，不生成虚假融入任务。
- 工资、绩效等仍执行独立的可见性和验证要求。
- 证明、住房借款、档案等独立办理事项通过服务大厅或相关内容页的操作进入，不新增第七个 Tab。

### 4.5 活水平台（WS-04，P0 入口；智能匹配等按 P2）

- 独立于员工自助的固定入口，保留职位搜索、筛选、职位详情、简历维护、投递与进度能力。
- 岗位类型包括内部招聘、举贤荐能、海外机会、管理岗竞聘、内部推荐。
- 浏览岗位无需先开启对话；“帮我分析匹配度”等操作可将已选岗位与授权简历作为显式上下文进入对话。
- 投递须展示岗位和最终材料并确认；生成推荐或打开职位不等于已投递。

### 4.6 服务大厅（WS-05，P0）

服务大厅是传统 GUI 业务的集中入口，以角色 Tab 组织入口组合。建议名称为“员工服务、管理者服务、HR 服务、薪酬 COE 服务”，名称可评审，角色 Tab 机制已确认。

| 角色 Tab | 入口组合 | 打开后的工作区 |
|---|---|---|
| 员工服务 | 人事服务、薪酬福利、绩效与改进、学习发展等 | 对应查询、表单、记录或外部系统 |
| 管理者服务 | 团队管理、招聘、关怀、出勤、动态、人才盘点、发展、结构、审批 | 对应团队业务页与明细 |
| HR 服务 | 组织岗职、人员全旅程、薪酬社保、培训发展、报表 | 专业列表、表单、分析或承接系统 |
| 薪酬 COE 服务 | 薪酬设计、定调薪、档案、奖金、年度调薪、福利、洞察报告 | 授权专业业务页或承接系统 |

- 只展示当前用户已获授权的角色 Tab；多角色用户可自由切换已授权 Tab，单角色用户不显示无权限选项。
- 切换 Tab 只改变服务入口组合，不改变当前身份、权限、首页或员工自助数据。
- 各 Tab 内按业务域分类；同一服务可在多个角色组合出现，但服务标识、数据和流程保持一致。
- 服务卡片展示名称、简短用途和可用状态；支持按名称/关键词查找，常用服务配置收敛在大厅内。
- 活水平台保持独立入口，大厅可提供指向它的快捷链接，不维护第二套职位和投递数据。
- 点击业务入口在右侧工作区打开对应页面，保留侧栏、来源 Tab 和返回路径；必须外跳的系统明确标识。
- 未接通、无适用业务或暂时不可用的服务展示真实状态，不能用通用演示列表冒充已具备业务能力。

### 4.7 对话与 GUI 的协同工作（WS-06，P0）

1. 从对话进入 GUI：回答中的“查看明细”“编辑申请”等动作打开关联业务页，沿用已确认对象与条件。
2. 从 GUI 进入对话：用户点击“问 AskHR / 让 AI 协助”，显式携带当前对象、期间和业务编号；用户能看见携带了什么上下文。
3. 若当前会话与该业务匹配，可继续原会话；否则默认新建带上下文的会话，避免污染其他事项。
4. 简短查询、草稿确认和结果卡片可内嵌消息；复杂表格、长表单和报告在工作区中展开，提供返回原会话入口。是否采用可并排的辅助面板留待设计验证，不作为必需布局。
5. GUI 与 AI 共用同一业务草稿、单号和最新状态，不重复生成申请；修改关键字段使旧确认失效。
6. 切换固定导航不取消已提交或正在执行的任务；执行可通过历史会话和待办继续查看。
7. 会话归档仅影响对话列表，不撤回业务；取消生成也不等于撤回已提交申请。

### 4.8 旧功能迁移与首页收敛

| 旧原型位置/功能 | 新位置 | 处理原则 |
|---|---|---|
| 员工、管理者、HR、COE 顶层视图 | 统一工作台＋大厅角色 Tab | 不保留顶层角色门户 |
| 各门户独立 AskHR 和历史对话 | 左侧统一对话管理＋右侧会话 | 统一会话与上下文 |
| 员工个人服务页面 | 员工自助六个 Tab | 保留核心业务内容 |
| 活水平台 | 左侧独立入口 | 与其他页面共享岗位与投递数据 |
| 管理者团队看板 | 大厅管理者服务中的具体业务页 | 可从对话直接打开，无独立顶层团队门户 |
| HR/COE 专业菜单和报表 | 大厅对应角色 Tab 下的业务页 | 逐项确定接入方式和深度 |
| 常用服务和配置 | 服务大厅内 | 不占用首页主区域 |
| 任务待办 | 首页简表＋全部待办二级页 | 只保留基础处理入口 |
| 我的申请 | 大厅入口/相关业务记录页/对话查询 | 与待办区分，不另设顶层导航 |
| 人资头条、公告 | 政策查询、服务大厅相关入口或对话引用 | 不新增顶层新闻入口，不放首页信息流 |
| 生日、周年与关怀 | 服务大厅相关服务及必要提醒 | 不在首页铺设关怀卡片 |
| 移动端 | 暂不纳入 | 不定义移动交互与验收 |

## 5. 核心用户流程

### 5.1 政策咨询并进入办理

1. 员工在首页输入“年假怎么申请”，或从左侧继续已有对话。
2. AskHR 根据任职主体、地区、员工类型和制度版本定位适用政策。
3. 返回结论、适用条件、来源与生效时间；按授权查询本人余额。
4. 用户点击“申请年假”，进入带有已知信息的草稿。
5. 提交后生成业务编号并进入“我的申请”。

完成条件：用户能够从答案追溯政策，并进入正确业务，不需重复输入已确认信息。无法确定适用制度时先澄清。

### 5.2 一句话请假

1. 员工输入“帮我请下周五一天年假”。
2. 系统解释相对日期，展示具体年月日、假期类型、时间段和时长。
3. 查询余额、排班和冲突；补问事由、交接人等必填信息。
4. 展示可编辑草稿、预计审批路径及校验结果。
5. 用户明确确认后提交；返回真实单号和当前审批节点。
6. 审批结果同步“我的申请”和考勤；符合条件时允许撤回。

完成条件：业务系统接受申请并可查询状态；打开会话、填好草稿、出现成功提示均不等于完成提交。

### 5.3 查询工资并解释变化

1. 员工问“这个月工资为什么少了”。
2. 确定月份，完成规定的敏感信息验证。
3. 展示本人对应期间的工资明细和可用对比项。
4. 基于有来源的项目说明差异；数据不足时说明缺口。
5. 仍有争议时，由用户确认转交薪酬服务人员，并保留问题与必要上下文。

完成条件：员工能够核对差异依据；涉及申诉或更正时产生可追踪服务记录。

### 5.4 管理者处理团队异常

从服务大厅“管理者服务”打开团队出勤，或直接在首页向 AI 提问 → 选择团队与期间 → 查看出勤/加班异常 → 下钻授权成员 → 查看事实与规则 → 发起沟通、补卡提醒或审批 → 跟踪状态。

完成条件：汇总、明细与处理回执一致；无权查看的成员和字段不通过问答、图表或导出泄露。

### 5.5 HR/COE 发起分析与专业流程

从首页对话发起，或从服务大厅“HR 服务 / 薪酬 COE 服务”打开专业业务 → 指定范围、期间和问题 → 确认指标口径 → 查询授权数据 → 返回异常与依据 → 生成报告草稿或专业系统表单 → 业务人员复核 → 按既定审批流程办理。

完成条件：报告可追溯数据，定调薪等操作仍由授权人员确认并履行审批。此流程为建议目标，原型只展示了部分入口。

## 6. 统一智能体核心功能需求

### AI-01 统一对话与意图识别（P0）

**原型依据：** 多角色页面均有 AskHR、猜你想问，以及“查政策、查个人信息、提流程、问课程、找人才”；员工有独立助手抽屉、历史会话和新对话。员工回复由 `aiAnswer` 关键词匹配，HR/COE 的 `askSubmit` 主要触发提示。

**目标要求：**

- 接受自然语言，识别咨询、查询、办理、进度、学习/人才搜索及分析诉求。
- 读取当前用户、角色、授权范围和页面上下文；不能以自然语言指定身份绕过授权。
- 支持多轮补充、修改条件、取消当前办理和重新开始。
- 识别不清时给出候选业务或关键追问，不虚构查询结果。
- 历史会话仅本人可见；切换账号后不得保留前一账号的可访问内容。
- 进入业务页后保留已确认信息与来源；返回会话时可以继续办理。

**验收：** 输入“查年假”应能区分政策与本人余额诉求；“改成下午”应修改当前草稿而不是创建另一笔申请。

### AI-02 可追溯政策问答（P0）

**现状：** 桌面端有政策问答话术；尚未体现真实检索和引用验证。

**目标要求：**

- 按问题检索制度，展示结论、文档标题、条款位置、适用范围和版本/生效日期。
- 区分正式制度、操作指引和 AI 总结；提供原文入口。
- 遇到版本冲突、制度失效或适用主体不明时明确说明并补问或交接人工。
- 对个人资格的判断同时依据正式规则和本人数据，不能仅靠通用话术作承诺。

**验收：** 在缺少适用制度时不能回答“符合申请资格”；更新制度后，新会话使用有效版本。

### AI-03 授权数据查询与解释（P0；薪酬明细 P1）

- 本人可查基础档案、假期余额、考勤、申请状态；逐步开放工资、社保公积金、绩效、任职资格和学习记录。
- 管理者按授权查询团队指标、成员与业务状态；HR/COE 按职责查询专业数据。
- 查询结果显示对象、期间、单位、更新时间和数据来源；解释与数据事实分别呈现。
- 查询条件不完整时澄清，查不到时给出空结果，接口失败时不能回退为演示数据。
- 涉及隐私的问答正文、历史摘要和通知预览遵循相同脱敏规则。

**验收：** “我的年假还有多少”与假勤页面同一时点数值一致；查询无权团队的数据应被拒绝。

### AI-04 服务定位与跨系统衔接（P0）

- 维护服务名称、同义表达、分类、适用用户、办理条件、所需材料、承接系统、入口和可执行动作。
- 将“我要开收入证明”等表达映射到正确服务，区分“可以代办”和“需要进入专业系统”。
- 支持带上下文跳转；正式 SSO 失败应提示重试或重新认证，不显示已打开成功。
- 暂不支持的服务仍能提供准确指引和承接方。

**验收：** 同一业务从问答和服务大厅进入相同承接流程；不可用服务有明确说明。

### AI-05 业务草稿与受控执行（P0，以请假为首个闭环）

**现状：** 员工请假表单有日期、时段、事由、交接人和余额校验，并写入内存记录；`aiLeaveDraft` 只开启带确认选项的演示会话，未形成真实语义填单。

**目标要求：**

- 将自然语言抽取为结构化字段，展示具体值，允许逐项修改。
- 根据实际业务校验必填、余额、时间冲突、附件、适用范围和审批链。
- 显示“将办理什么、为谁办理、提交哪些信息”，经用户确认再执行。
- 提交后仅以业务系统回执认定成功，展示单号、状态、时间和详情入口。
- 重复点击或重复消息不能造成重复提单；超时结果未知时先核查原提交再重试。
- 调薪、审批、群发等影响其他人的动作必须在执行前展示范围与结果预览。

**验收：** 草稿未确认不能提交；连续点击提交只产生一笔业务；失败时保留草稿且不显示成功。

### AI-06 任务、申请与结果跟踪（P0）

- 汇总我的申请、待我处理、待补充材料、审批中及已完成事项。
- 每项包含来源系统、业务类型、标题、编号、当前节点、处理人/部门、截止时间和状态。
- 支持按类型、状态、时间筛选；自然语言可问“我的证明办到哪了”。
- 对催办、撤回、补材料和审批等动作，按源系统规则及权限开放。
- 结果变更同步列表与会话；源系统暂时不可用时展示最后更新时间。

**验收：** 同一单据在会话、待办和业务详情中状态一致；终态单据不继续展示可提交或重复审批动作。

### AI-07 场景推荐与主动提醒（P1）

- 结合入职阶段、待办、假期临期、绩效周期、学习缺口等推荐问题或下一步动作。
- 说明推荐依据，支持关闭或调整提醒，避免重复催促。
- 提醒只呈现必要信息，不在通知预览暴露工资、绩效或人才风险标签。
- 对生日、周年等社交关怀，生成祝福草稿并提供收件人预览，确认后发送。

### AI-08 辅助分析与报告（P2）

- 管理者可查询团队结构、人才分布、出勤趋势和发展进展。
- HR/COE 可进行薪酬结构与异常分析、行业对标和报告生成。
- 返回指标定义、期间、筛选范围、数据来源及明细入口；区分事实、相关性与建议。
- 薪酬方案、绩效评价和人才判断提供辅助建议，不能直接改变员工待遇或评价。
- 报告资产保存版本、作者、范围和权限；行业数据来源、更新频率和可用权利待确认。

### AI-09 人工交接与运营管理（P1，建议新增）

- 无依据、连续失败、争议或用户主动要求时提供人工入口。
- 经用户确认传递问题、业务编号和必要上下文，返回服务记录及处理状态。
- 维护政策版本、服务目录、业务动作与权限配置，支持停用错误知识或不可用动作。
- 记录失败原因与用户反馈；评估问答准确性、办理成功率和转人工原因。

| 薪酬配置与福利 | 序列系数对应薪酬区间、薪酬标准系数、交通补贴、职称补贴、特殊薪酬项目 | 资格、金额、适用期与计算规则 |

以上主要来自 COE 菜单 `COE_PAY_MENU`。应先明确专业系统承担哪些业务，再决定智能体可查询、可生成草稿或可提交的动作。

## 8. 关键业务对象与规则

| 对象 | 最小必要信息 | 关键规则 |
|---|---|---|
| 用户与角色 | 员工标识、任职主体、组织、岗位、角色、授权范围 | 角色、组织、字段和动作共同决定权限 |
| 政策 | 标题、版本、条款、生效/失效日期、适用主体、来源 | 只使用适用且有效版本，历史版本可追溯 |
| 服务 | 服务标识、名称、分类、适用人群、材料、承接系统、动作范围 | 同一服务在各入口统一映射 |
| 业务草稿 | 业务类型、对象、字段、材料、校验、确认状态 | 未确认不得执行；更改关键字段后重新确认 |
| 申请/审批 | 业务编号、来源、申请人、节点、状态、时间、结果 | 以源系统为准；状态改变后更新可用动作 |
| 会话/任务 | 所属用户、问题、上下文、关联业务、执行状态 | 用户隔离，敏感内容受控，保留期限待确认 |
| 指标/报告 | 指标定义、期间、范围、来源、更新时间、版本 | 汇总和明细可核对，导出遵循权限 |

请假规则必须由正式排班、节假日和休假制度确定，不直接沿用原型工作日算法；调休的小时/天换算也不可将原型中的每天 8 小时视为统一制度。工资、个税、社保和资格判定同样以正式规则与权威业务数据为准。

## 9. 交互要求

1. **输入与推荐：** 空输入不可发送；快捷问题能填入或发起对应会话，不能直接执行提交。
2. **回答状态：** 区分理解中、查询中、待补充、待确认、执行中、完成、失败，允许取消尚未提交的办理。
3. **草稿卡片：** 明确标注草稿，突出对象、日期、金额/时长、必填缺口与提交影响；支持进入完整表单。
4. **确认：** 审批、申请提交、修改档案、发消息、群发和薪酬相关动作展示操作对象与范围后确认。
5. **反馈：** 成功展示真实编号或回执；失败保留输入，标注错误字段或失败阶段，并提供下一步。
6. **导航：** 页面、抽屉、详情支持返回；保留筛选和填写内容，存在未保存内容时提醒。
7. **常用服务：** 在服务大厅内选择、移除、排序、重置并保存，不返回首页铺设；员工原型与 HR/COE 的数量上限不同，正式规则待确认。
8. **图表与表格：** 指标注明单位和统计期间；图表支持查看数值与明细，不只用颜色表达风险。
9. **敏感数据：** 工资和绩效按规则遮罩；验证应使用企业认可的身份机制，原型演示密码不得沿用。
10. **桌面可访问性：** 更多服务支持点击和键盘展开，主要入口可聚焦，长标题可完整查看；窄桌面窗口可收起侧栏，保持工作区可用。

## 10. 状态、异常与边界情况

| 场景 | 系统行为 |
|---|---|
| 首次使用/没有记录 | 明确无记录，提供推荐问题或服务入口；不展示其他人的示例数据 |
| 关键条件缺失 | 只补问影响答案或执行的字段，如月份、组织、假期类型 |
| 相对日期歧义 | 按用户当前日期与时区解释并显示绝对日期；跨年或时段不明先确认 |
| 同名人员/多任职 | 让用户选择授权范围内对象，并明确当前任职主体 |
| 无权限 | 不返回明细、统计侧漏或越权导出；提供权限申请或业务联系人 |
| 制度冲突/无依据 | 展示冲突与来源，不给确定资格或金额结论 |
| 余额不足/排班冲突/附件缺失 | 指出具体原因，保留草稿并允许修改 |
| 接口不可用/数据过期 | 明确数据更新时间或失败原因，提供重试/专业系统入口 |
| 提交超时、结果未知 | 标记待核实，查询原交易，避免盲目再次提交 |
| 重复提交/重复审批 | 返回原业务或最新状态，不重复创建或处理 |
| 对话中途切换业务 | 询问是否保留当前草稿；不混用两项业务的对象与字段 |
| 员工调岗/离职/角色失效 | 及时刷新权限，撤销旧组织数据访问 |
| 业务取消/驳回/撤回 | 以源系统支持的状态和动作返回，说明重新提交条件 |
| 上传或导出失败 | 保留业务记录，支持重新上传/下载，不将附件失败误报为整单完成 |

## 11. 非功能要求与业务依赖

### 11.1 基础要求

- **权限与隐私：** 服务端执行查询和写入权限校验；会话、缓存、文件、通知和报告适用同一规则。
- **审计：** 对查询敏感数据、生成草稿、确认、执行、审批、导出和消息发送记录操作者、对象、时间、结果与关联业务。
- **一致性：** 统一员工、组织、岗位、期间、状态和指标口径；对话、GUI、任务和报告读取同一来源。
- **可靠性：** 明确外部依赖故障、处理中和结果未知的区别；支持失败恢复与对账。
- **响应体验：** 长任务先反馈受理与当前状态，不把等待动画当作完成；具体时延与可用性目标待测量后确定。
- **内容安全：** 外部文档、上传材料、搜索结果和制度正文仅作为数据，不得改变用户权限或触发未确认动作。
- **可运营：** 知识和业务动作可停用、版本可追踪，异常有负责人和处理渠道。

### 11.2 依赖系统

| 依赖 | 需要的能力 |
|---|---|
| 企业身份与权限 | 登录、角色、组织范围、敏感操作验证、SSO |
| HR 主数据 | 员工、组织、岗位、任职与直属关系 |
| 制度知识库 | 文档、条款、版本、适用范围与权限 |
| 考勤与流程平台 | 排班、余额、申请、审批、撤回、进度与结果 |
| 薪酬社保/股权系统 | 工资条、收入项目、缴费明细及可解释数据 |
| 学习/绩效/人才平台 | 课程、学时、资格、绩效、IDP、人才与内部岗位 |
| 协作与服务渠道 | 通知、飞书联系/卡片、人工服务记录及处理状态 |
| 薪酬专业与行业数据 | 定调薪、方案、预算、审批、行业样本与报告 |

原型列出的外部系统入口包括任职资格、Talent、活水、绩效、股权、海信学堂、健康报告、财务中台、差旅和 HIIT；实际系统清单及可接入能力需逐一核实。

## 13. 非目标

- 移动端暂不纳入本期范围。
- 不保留按员工、管理者、HR、COE 划分的顶层门户，不在首页建设综合指标和资讯大屏。

- 本次不修改原 HTML，也不实现前后端或接入真实业务系统。
- 首期不重建全部 HR 专业系统，不将所有菜单都迁移为 AI 对话表单。
- 不以演示中的工资、税率、假期、资格或审批时限作为正式制度。
- 不让 AI 自主审批、决定调薪、确定绩效或对员工做出最终人事决定。
- 不将发起动作、显示提示、生成草稿或打开入口等同于业务办理成功。

## 14. 待确认问题与默认假设

### 14.1 原型中的明确差异

| 问题 | 证据 | 处理建议 |
|---|---|---|
| 业务口径仍为演示 | 桌面 `aiAnswer` 中的发薪日、假期额度与资格话术为固定示例 | 从正式制度和个人数据获取，本期不展开移动端差异 |
| 常用服务数量不同 | 员工为不限数量，HR/COE 最多 8 个 | 明确统一上限还是按角色分别设置 |
| 九宫格定义不统一 | 存在能力、潜力等不同文案和实现线索 | 明确正式维度、评分来源、阈值及校准权限 |
| 数据与日期为样例 | 部分日历固定 2026 年 9 月，指标与待办分别使用静态数据 | 正式产品使用真实期间、来源与统一统计口径 |
| 专业页面深度不同 | 有专门组织岗职页，也有 `openBizPage` 通用列表和建设中入口 | 建立接入清单，逐项明确查询、跳转或可执行边界 |

### 14.2 产品决策待确认

1. 首期优先服务哪些角色、组织和高频事项？请假是否作为首个真实办理闭环？
2. 智能体代办边界是什么：只定位、可填草稿、可提交，还是允许部分批量操作？
3. 各域权威系统与责任人是谁？是否可获取查询、提交、审批和状态回写能力？
4. 多主体、多地区、多任职和矩阵组织下的权限及政策适用规则如何定义？
5. 薪酬、绩效、人才标签、生日和健康类信息的可见范围及验证机制是什么？
6. 证明是否需要电子签章或人工用印，如何领取和核验？
7. 管理者审批、转正、人才盘点和调薪的正式状态、审批链与生效规则是什么？
8. 人工交接由 HRBP、共享服务还是业务专员承接，服务时限如何定义？
9. 首页待办的展示上限、排序和全量待办筛选如何定义？建议默认展示最多 5 条。
10. 会话、业务审计、附件、报告保留多长时间，用户可删除哪些内容？
11. 行业薪酬数据来自何处，是否具备持续更新和企业使用权限？
12. 哪些交互属于原型演示辅助功能，例如三级菜单重命名，不应直接作为正式配置功能？

### 14.3 为推进评审采用的默认假设

- 按用户已确认的统一工作台架构推进；六个员工自助 Tab 和大厅角色 Tab 是 GUI 访问方式，AskHR 是主要业务入口。
- 新对话与首页进入同一空白会话页；历史会话不会因返回首页而丢失。
- 对话管理先支持搜索、重命名、置顶和归档；删除与保留策略待企业确认。
- 真实业务系统是数据与流程状态的权威来源，智能体负责理解、协助与衔接。
- 权限先于查询和执行校验；有管理者角色不等于有全员薪酬查看权。
- 用户提交或审批前能够查看准确对象与最终内容，确认后才执行。
- 优先打通少量高频闭环，再扩展到专业分析和复杂人资业务。
